# Data types, keys, and constraints

Use this reference when choosing engine-specific DDL. Record the database product,
version, storage engine, collation, and relevant connection settings before treating
syntax or enforcement as portable. Examples below are choices, not mandatory defaults.

## Type decisions by engine

| Intent | PostgreSQL | MySQL 8.4 / InnoDB | SQLite | SQL Server |
|---|---|---|---|---|
| Generated integer key | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | `BIGINT AUTO_INCREMENT` | `INTEGER PRIMARY KEY` | `BIGINT IDENTITY(1,1)` |
| Exact amount | `NUMERIC(p,s)` | `DECIMAL(p,s)` | Integer minor units with explicit currency/scale | `DECIMAL(p,s)` |
| Boolean | `BOOLEAN` | `BOOLEAN` is a numeric alias; constrain the permitted values if needed | `INTEGER CHECK (flag IN (0,1))` | `BIT` |
| Bounded text | `VARCHAR(n)` when the bound is a domain rule, otherwise `TEXT` | `VARCHAR(n)` with deliberate character set/collation | `TEXT`; enforce length with `CHECK` | `NVARCHAR(n)` for Unicode |
| Calendar date | `DATE` | `DATE` | Documented ISO date text or application encoding | `DATE` |
| Event instant | `TIMESTAMPTZ` | `TIMESTAMP(6)` with controlled session zone, or UTC-by-contract `DATETIME(6)` | UTC text or integer epoch with documented unit | `DATETIMEOFFSET(p)`, or UTC-by-contract `DATETIME2(p)` |

Generated values do not replace a `PRIMARY KEY` or `UNIQUE` constraint. Choose integer
capacity from expected lifetime volume; never promise generated IDs are gap-free.
For UUIDs, choose native/character/binary representation for the actual engine and
driver, and keep serialization and comparison rules consistent.

Do not assume a declared SQLite `DECIMAL` gives exact fixed-point arithmetic, or
that `VARCHAR(20)` enforces a 20-character bound. SQLite `STRICT` tables allow only
`INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB`, and `ANY`. Use integer minor units for exact
money where the currency scale is known; a two-decimal assumption does not fit every
currency. [SQLite quirks](https://www.sqlite.org/quirks.html),
[STRICT tables](https://www.sqlite.org/stricttables.html).

An instant, a local appointment, and a date-only value are different facts. PostgreSQL
`TIMESTAMPTZ` stores an instant and displays it in the session zone; it does not retain
the original zone name. Store an IANA zone separately when future local schedules need
daylight-saving rules. [PostgreSQL date/time](https://www.postgresql.org/docs/current/datatype-datetime.html).
MySQL `TIMESTAMP` converts using the connection time zone and has a narrower range
than `DATETIME`; verify that range against the domain.
[MySQL date/time](https://dev.mysql.com/doc/refman/8.4/en/datetime.html).
SQL Server `timestamp` means row-version data, not a clock time. Use the appropriate
date/time type. [SQL Server date/time](https://learn.microsoft.com/en-us/sql/t-sql/data-types/date-and-time-types).

## Integrity decisions

For every column, record: meaning, type/units, required versus optional, valid range,
and whether a default expresses a real business rule. A default fills an omitted
value; it does not reject explicit `NULL`. Do not fill unknown data with arbitrary
zeroes, empty strings, or timestamps just to satisfy `NOT NULL`.

For every candidate business key, decide its scope and comparison rules. For example,
an external number may be unique within an account, requiring
`UNIQUE(account_id, external_number)`, rather than global uniqueness. Soft deletion,
nullable keys, and case-insensitive identity need engine-specific choices; do not
infer an email uniqueness rule merely from a column name.

| Constraint | Decision to document | Common omission |
|---|---|---|
| Primary key | Stable row identity and component columns | Surrogate key exists but is unconstrained |
| Unique | Business scope and treatment of case/NULL | Global uniqueness where tenant-scoped uniqueness was intended |
| Foreign key | Parent candidate key, child optionality, lifecycle | Types/collations incompatible or parent key not unique |
| Check | Row-local invariant and NULL behavior | `CHECK (amount > 0)` alone still allows NULL |
| Not null | A value is always required | A default is mistaken for a requirement |

For PostgreSQL, `CHECK` is satisfied by true or unknown, so pair it with `NOT NULL`
when missing values are forbidden. Cross-row business invariants generally need
unique/exclusion constraints, transaction logic, or another explicit mechanism;
do not hide them in an ordinary row check.
[PostgreSQL constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).

## Foreign-key lifecycle and indexes

- Choose `CASCADE` when a child truly belongs to the parent lifecycle, not merely
  because deletion would otherwise fail. Preserve audit/history requirements.
- Choose `SET NULL` only when absence is meaningful and affected columns are nullable.
  For composite keys, decide whether mixed NULL/non-NULL values are allowed.
- Choose `NO ACTION` or `RESTRICT` to prevent invalid deletion. They are not universally
  interchangeable in timing; SQL Server uses `NO ACTION`, not `RESTRICT`.
- Usually keep identifiers immutable. If updates are allowed, specify their behavior.
  Explicit `ON UPDATE NO ACTION` is also a valid documented decision.
- Use table-level `FOREIGN KEY (...) REFERENCES ...` for portable declarations.
  MySQL inline column `REFERENCES` does not create the intended enforced foreign key;
  InnoDB table-level FKs and engine support must be verified.
- Enable and verify `PRAGMA foreign_keys = ON` per SQLite connection before a
  transaction. Ordinary SQLite rowid tables have historical nullable-PK exceptions;
  use explicit `NOT NULL` where required, `INTEGER PRIMARY KEY`, or appropriate
  `STRICT`/`WITHOUT ROWID` tables.

Check the existing index inventory before adding an FK index. An index on `(account_id,
sequence)` already provides a leading lookup on `account_id`; the suffix alone does
not provide the same access path. `INCLUDE` columns and expression/partial indexes
are not automatically equivalent to a full leading-key index. Evaluate workload
and write cost rather than adding an index blindly. InnoDB creates a supporting child
index when needed; PostgreSQL and SQL Server do not automatically create one for
every FK. Small or rarely touched tables may have a justified exception.

Sources: [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html),
[MySQL foreign keys](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html),
[MySQL CREATE TABLE](https://dev.mysql.com/doc/refman/8.4/en/create-table.html),
[SQL Server CREATE TABLE](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-table-transact-sql).

## Naming and verification

Use project conventions first. If none exist, prefer unquoted snake_case identifiers
and descriptive prefixes: `pk_<table>`, `fk_<child>_<parent>`, `uq_<table>_<columns>`,
`ck_<table>_<rule>`, and `ix_<table>_<columns>`. Add the relationship role when two FKs
target the same parent. Check the engine's identifier-length limit before truncating;
retain uniqueness after truncation. Prefer `sales_order` over a quoted reserved word.

Run the [local linter](../scripts/validate_schema.py) for structural omissions. Then
apply the DDL to a disposable database of the actual product/version and verify
duplicates, missing parents, forbidden NULLs, invalid ranges, and delete/update
behavior. Lint does not validate expression semantics, collations, or runtime locking.
